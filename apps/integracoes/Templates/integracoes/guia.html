Guia de integrações

O centro de integrações liga o VistoGest a serviços externos (mensagens, e-mail, pagamentos, APIs vossas). Cada integração tem credenciais cifradas, um teste de ligação, limites diários, registo de todas as chamadas e um endereço de webhook para receber eventos.

  1. Configurar — preencher credenciais e opções.
  2. Testar ligação — valida as credenciais sem activar.
  3. Activar — só então o sistema passa a usá-la.
  4. Monitorizar — em Logs e Webhooks.

Pré-requisitos

  • Permissão: o seu cargo precisa de Pode aceder às configurações.
  • Chave de cifra (administrador do servidor): defina ENCRYPTION_KEY no .env. Para gerar uma: 
    python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
    Guarde-a em cofre: se a perder, as credenciais guardadas deixam de ser recuperáveis. Para rodar a chave, ponha a nova primeiro, separada por vírgula (NOVA,ANTIGA) e volte a guardar as credenciais.
  • HTTPS público: para receber webhooks, o domínio da empresa tem de ser acessível pela Internet em HTTPS. Em desenvolvimento use um túnel (ngrok/cloudflared) e registe o domínio do túnel no tenant.
  • Contas nos fornecedores: cada serviço exige conta/credenciais próprias (ver cada tipo abaixo).

Passo a passo (qualquer integração)

  1. No Painel, escolha o serviço e clique em Configurar.
  2. Comece em ambiente Teste (sandbox) com credenciais de teste, quando o fornecedor as oferece.
  3. Grave e clique em Testar ligação. Se falhar, abra o log da chamada (cabeçalhos e corpo estão mascarados).
  4. Se o serviço envia eventos, copie o URL do webhook (página de detalhe) para o portal do fornecedor.
  5. Clique em Activar. Passe a Produção apenas depois de testar tudo com credenciais reais.
  6. Defina um limite diário adequado para evitar custos inesperados.

Webhooks de entrada

Cada integração com webhook tem um URL único, por exemplo:

{{ exemplo_url }}

Para fornecedores genéricos, o remetente envia um POST com o corpo (JSON) e o cabeçalho X-Webhook-Signature: sha256=<hex>, onde o hex é o HMAC-SHA256 do corpo exacto com o segredo mostrado em «Gerar novo segredo HMAC». Opcionalmente X-Webhook-Id (identificador único, para ignorar reenvios).

{% verbatim %}
# Python
import hmac, hashlib, json, requests
corpo = json.dumps({"evento": "pagamento.confirmado", "referencia": "123"}).encode()
assinatura = "sha256=" + hmac.new(SEGREDO.encode(), corpo, hashlib.sha256).hexdigest()
requests.post(URL, data=corpo, headers={"Content-Type": "application/json",
              "X-Webhook-Signature": assinatura, "X-Webhook-Id": "evt_001"})

# Shell
BODY='{"evento":"ping"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SEGREDO" | sed 's/^.* //')
curl -X POST "$URL" -H "Content-Type: application/json" -H "X-Webhook-Signature: sha256=$SIG" -d "$BODY"
{% endverbatim %}
  • Respostas: 200 aceite (também em reenvios duplicados), 401 assinatura inválida, 404 token desconhecido ou integração inactiva, 413 corpo > 1 MB.
  • WhatsApp (Meta) usa o seu próprio esquema: X-Hub-Signature-256 com o App Secret, e verificação por hub.verify_token. Twilio usa apenas o token do URL.
  • Eventos recebidos ficam em Webhooks; os que falharem podem ser reprocessados.

Usar nas outras partes do sistema

{% verbatim %}
from apps.integracoes.services.api import enviar_mensagem, emitir_evento

# WhatsApp / SMS / e-mail (usa a 1.ª integração de mensagens activa, ou escolha com canal=)
ok, msg = enviar_mensagem("244923000000", "A sua factura FR 2026/15 está pronta.")
ok, msg = enviar_mensagem("cliente@exemplo.ao", "Segue a factura.", canal="sendgrid", assunto="Factura")

# Evento para o vosso sistema (webhook de saída)
emitir_evento("venda.finalizada", {"numero": "FR 2026/15", "total": "15000.00"})
{% endverbatim %}

As duas funções nunca levantam excepção: devolvem sucesso/falha e tudo fica nos logs. Lógica de negócio para eventos recebidos implementa-se em processar_webhook() do conector em services/providers.py.

Para adicionar um serviço novo: crie uma classe com @registrar("codigo") em providers.py, acrescente a entrada em services/catalogo.py e execute seed_integracoes.

Segurança e boas práticas

  • As credenciais são cifradas (Fernet) e nunca são mostradas depois de gravadas; deixar um campo secreto em branco mantém o valor.
  • As chamadas de saída só aceitam https e bloqueiam endereços internos/privados (protecção contra SSRF); não seguem redirecionamentos.
  • Os logs mascaram cabeçalhos e campos sensíveis. Use um limite diário e analise os erros com regularidade.
  • Use credenciais com o mínimo de permissões e rode-as se alguém deixar a equipa. «Remover credenciais» desactiva a integração imediatamente.
  • Se suspeitar que um segredo de webhook foi exposto, gere um novo e actualize o remetente.

Problemas comuns

«ENCRYPTION_KEY não configurada»Defina a variável no servidor e reinicie a aplicação.
«Não foi possível decifrar»A chave mudou. Reponha a chave anterior (ou NOVA,ANTIGA) ou volte a introduzir as credenciais.
Teste falha com HTTP 401/403Credencial errada, expirada ou sem permissões; confirme o ambiente (teste vs. produção).
«Falha de ligação (timeout)»Aumente o timeout (máx. 120 s) ou verifique o estado do fornecedor.
«Endereços internos não são permitidos»O URL aponta para a rede interna. Use o endereço público HTTPS.
«Limite diário excedido»Aumente o limite na configuração; o contador reinicia à meia-noite.
Webhook devolve 401Assinatura calculada sobre o corpo errado (tem de ser os bytes exactos) ou segredo desactualizado.
Webhook devolve 404Token errado ou integração desactivada. Confirme também que o caminho /integracoes/webhook/ não está atrás do login do sistema.
WhatsApp: mensagem aceite mas não entregueFora da janela de 24 h é obrigatório usar um modelo aprovado pela Meta.
